## Unsourced statements in the draft
1. **REJECT.** §2 table, Car parking: "Yes, one space per spot [C66]". C66 only says the Type attribute can mark a space as a parking space. Nothing says one space per spot. Drop "one space per spot".
2. **REJECT.** §12 Venue row: "tenant; one API key per venue". This is wrong as written. Each key belongs to one venue, but a venue can create and revoke several keys (getting-started article: "Manage your API keys", "Revoking a key ... Any integrations using that key"). Correct it to "each API key is scoped to one venue; a venue may have many keys" [C4, C33].
3. **Minor, cite fix.** §9: "A key has admin-level visibility of its venue, including admin-only custom fields [C4]." The page supports this in the BookingOccurrenceCustomField model ("Fields the venue marked admin-only are deliberately included ... it carries admin visibility"), but C4 does not cover it. Add a ledger claim, or cite the model section, or C37's "admin-only custom fields".
4. **Minor, cite fix.** §13: "The webhooks help article only suggests pointing webhooks at them [C35]." It is supported by the page, not by C35's text. Use N2.
5. **Minor wording.** §10: "nested at most 3 deep" should be "at most 3 expanded fields in one path" (C12).
6. **Minor wording.** §1: "AllBooked is a sister product for venues that charge for bookings". The pricing page says "Skedda's solution for sports, studios, coworking, and community booking", with "Embedded pricing & payments" and "Membership management". Rephrase closer to the source. C39's ledger text covers only tiers.

Checked and OK without a ledger claim: in §4, the old article 4225747 really does return 404, both with and without the slug. The search snippet that calls the maps "vector-based (SVG)" comes from that dead article, so the draft was right not to cite it.

- **Booking (implicit):** it is correctly labelled INFERRED. Supported by WebhookBooking (bookingId, occurrences[]) and by BookingOccurrence repeating booking-level properties per occurrence (C15, C28).
- **BookingOccurrence → addOns[].asset → Asset:** the field exists in the BookingOccurrenceAddOn model, but C28's ledger text mentions only "addOns". The trace is acceptable, but C28's claim text should name BookingOccurrenceAddOn{asset, quantity}.
- **BookingOccurrence createdBy/lastModifiedBy → VenueUser:** the page supports it, and it falls under C28's "fields incl." wording. OK.
- **VenueUser createdBy/lastModifiedBy and tags → VenueUserTag:** supported by C31's model. OK.
- All other entities (Asset, AssetAttributes/AssetAttribute, AssetAddOnConfig, BookingOccurrenceConference, BookingType, VenueUserTag) trace to accepted claims (C24-C31, C56).
